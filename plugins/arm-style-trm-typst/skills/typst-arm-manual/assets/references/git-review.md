# Git 기반 TRM 갱신

기존 TRM을 갱신하거나 새 TRM을 Git 프로젝트에 만들 때 이 절차를 적용한다. 변경 수집은 매 실행 수행하고, 기존 TRM의 기술 내용 수정은 독립 reviewer 5명 중 최소 3명이 해당 후보의 반영에 찬성한 경우에만 한다. 최초 작성은 기존 문서와 비교할 변경이 없으므로 현재 소스의 초기 기술 범위와 필요한 그림을 후보로 검토한다.

## 기준과 변경 수집

1. 프로젝트 Git 루트, 문서 경로, 기술 대상 소스 경로를 식별한다. 문서 산출물, reviewer 자료, 캐시와 무관한 프로젝트는 기술 변경 범위에서 제외한다. Git worktree는 해당 worktree의 HEAD와 상태를 사용한다.
2. 기준은 사용자가 지정한 commit/기준일 → 저장된 갱신 상태 → 기존 TRM의 명시적 기준 commit/기준일 순으로 고른다. 날짜는 timezone과 함께 기록하고, 그 날짜 이전의 마지막 first-parent commit으로 해석한다. 날짜 경계에 맞는 commit이 없거나 기준이 HEAD의 조상이 아니면 임의 범위를 사용하지 말고 기준을 확인한다. 기준이 전혀 없으면 현재 소스를 초기 baseline으로 기록하며, 과거 변화 목록을 지어내지 않는다.
3. 아래 collector로 commit log, commit별 변경 파일, 기준..HEAD diff, staged/unstaged diff, untracked 파일 목록을 수집한다. HEAD와 dirty 상태를 함께 기록한다. 날짜는 `--base` 대신 `--since '2026-11-03T00:00:00+09:00'`를 사용한다.

   ```bash
   python3 /path/to/skill/assets/scripts/git_changes.py \
     --repo /path/to/repository --base FULL_COMMIT \
     --scope src --scope include \
     --output /path/to/review-workspace/change-set
   ```

   `--scope`는 Git 루트 상대 경로이며 여러 번 지정할 수 있다. 경로가 생략되면 저장소 전체를 조사하므로 문서 및 생성 파일을 후보에서 걸러낸다. collector는 기술적 중요성이나 반영 여부를 판단하지 않는다.
4. log의 제목만으로 판단하지 않는다. diff와 최신 소스를 읽고 추가·수정·삭제·이름변경을 모두 정리한다. ABI/API, 레지스터/비트필드, 데이터·제어 흐름, 상태 전이, 메모리 배치, 빌드·사용 절차, 제약·오류 계약의 변화를 찾는다. untracked 내용은 별도로 읽으며 commit된 변화로 표현하지 않는다. ignored 파일과 외부 저장소/submodule 내부는 Git diff로 검증되지 않을 수 있음을 명시하고, 시험 복사본에서는 기존 manifest 등 확인 가능한 근거까지만 보완한다. 일반 Git 프로젝트를 위한 절차를 시험 복사본의 예외에 맞춰 변경하지 않는다.
5. 변화가 없거나 모두 이미 문서화되어 있으면 그 사실도 검토 자료에 포함한다. 기준일만 바꾸거나 PDF를 재생성하여 갱신을 꾸미지 않는다.

## 후보와 독립 검토

- 후보마다 안정적인 ID, 변화의 전후 내용, commit/파일/줄 또는 diff 근거, 영향을 받는 TRM 절, 사용자에게 미치는 영향과 제안 문안/그림을 작성한다. 별개 변화를 하나로 묶어 투표를 우회하지 않는다.
- 기존 문서의 중요한 누락·오류 또는 필요한 다이어그램도 후보가 될 수 있다. 소스 변경과 구분하여 `documentation-gap`으로 표시하고 최신 소스 및 기존 본문으로 근거를 제시한다. 단순 미관 개선을 기술적 중요성으로 과장하지 않는다.
- **서로 다른 reviewer subagent를 정확히 5명 호출한다.** 같은 입력 묶음(변경 전체 목록, 관련 diff와 최신 소스, 기존 TRM, 후보들)을 주되, 다른 reviewer의 의견이나 예상 결론은 전달하지 않는다. 관점은 아키텍처·데이터흐름, ABI·호환성, 개발·운영, 근거·정확성, 문서 사용성으로 나눌 수 있으나 모두 각 후보의 반영 필요성과 중요성을 판단한다.
- 각 reviewer는 후보별 `approve` / `reject` / `abstain`, 근거, 중요성, 적용 시 조건을 반환한다. 변화가 없는 실행에서도 5명이 변경 없음 판단과 기존 문서의 중요한 누락 여부를 독립 확인한다. 주 agent는 reviewer 수에 포함하지 않는다.
- 동시 실행 한도보다 적은 수씩 나누어 실행해도 된다. Codex는 해당 환경의 subagent 도구, Claude는 해당 환경의 독립 agent 도구를 사용한다. 5명의 실제 검토를 실행할 수 없으면 가능하다고 가장하거나 주 agent가 다섯 표를 대신하지 않는다. 변경 수집·후보 준비까지 진행하고 TRM 수정은 보류하여 제한을 보고한다.
- **후보별 찬성 3표 이상일 때만 그 후보를 반영한다.** 기권·실패·미응답은 찬성에 포함하지 않으며 분모를 줄이지 않는다. 2표 이하이면 그대로 둔다. 조건부 찬성은 명시된 조건을 충족한 경우에만 센다. 제안의 의미·범위가 달라지면 동일 후보의 승인으로 처리하지 말고 다시 검토한다.
- 이미 설명된 내용, 구현에 영향 없는 refactor/format, 일시 로그, 무관한 변경은 보통 반영하지 않는다. 독자가 API/ABI를 잘못 사용하거나 새 기능·제약을 놓칠 정도의 변화는 중요한 후보가 된다. 자동화로 임계값을 낮추거나 찬성이 나올 때까지 결론을 유도하지 않는다.

## 반영, 기준 보존 및 인계

승인된 후보만 기술 문장·표·다이어그램·참조에 반영하고 기존 스킬의 build/check/렌더 검수를 수행한다. 검증된 결과를 전달하고 저장소 지침에 따라 해당 작업 파일만 커밋한다. 반영 후보가 없으면 TRM 본문과 PDF를 그대로 둔다. 검토를 위한 메타데이터는 본문 수정과 별개다.

갱신 상태는 TRM 배포 폴더 밖의 `.trm/<manual-id>/state.json` 등에 저장한다. 최소한 `review_base_commit`, `last_reviewed_head`, `last_published_source_commit`, 소스 scope, dirty 상태/근거, 미반영 후보 ID와 근거를 남긴다. Git source commit과 문서 자체의 publication commit을 혼동하지 않는다. dirty 소스를 반영했다면 commit만으로 재현 가능하다고 표현하지 말고 patch/hash도 기록한다.

기준을 이동해서 미반영 변화를 잃지 않는다. 미반영 후보가 남으면 기존 `review_base_commit`을 유지하여 다음 실행에서도 누적 diff와 현재 TRM을 대조한다. 반영·기반 소멸 등 모든 후보의 처리가 확인된 뒤에만 기준을 현재 source HEAD로 이동한다. 기준이 초기 설정뿐인 경우도 출처가 있는 baseline과 구분한다. 마지막 검토 HEAD는 TRM을 수정하지 않아도 갱신할 수 있다.

reviewer 응답·투표·집계는 별도 검토 작업 공간에 보관하고, **TRM 본문·부록·PDF·배포 ZIP에 넣지 않는다.** 최종 사용자 응답에는 반영/보류 결과를 짧게 알릴 수 있다. 기술 문서에는 최종 기술 사실과 출처만 남긴다.
