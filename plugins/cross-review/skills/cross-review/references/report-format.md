# 보고서 형식

## 먼저 읽히는 부분

1. 한두 문장으로 확정 문제 수·주요 영향·완료 상태를 적는다. 신규 결함이 없으면 그 사실을 먼저 밝힌다. 증거 없이 “완벽 구현”, “무결함”이라고 쓰지 않는다.
2. 문제를 중요도 순으로 제시한다. 각 항목은 구체적인 제목, 문제, 답변, 설명형 출처 링크로 구성한다. 확정 결함과 기각된 제안·확인 필요 사항을 구분한다.
3. 검증 결과·한계와 다음 결정만 짧게 남긴다. 파일 목록·장황한 용어 설명·진행 로그·리뷰 원문은 상세 영역으로 옮긴다. 넓은 표보다 짧은 문장으로 요점이 먼저 읽히게 한다.

### 문제와 답변의 길이·줄바꿈 및 두괄식 요약

- **두괄식 요약 원칙**: 문제와 호스트 최종 판정(해결책)은 독자가 즉시 핵심을 파악할 수 있도록 본문 맨 앞 첫 줄에 각각 **1줄짜리 문제**, **1줄짜리 해결책(수정방안)**을 명확하게 제시한다.
- **문제 본문 (항목당 최대 3줄)**:
  - 첫 줄에 **1줄짜리 핵심 문제**를 두괄식으로 기술한다(발생 조건과 결함 요점).
  - 이어지는 줄(최대 2줄)에 구체적 영향, 정적 분석/재현 여부 등 필수 부연을 담는다.
- **답변 본문 (항목당 최대 10줄)**:
  - 상대 관찰자의 검토(동의/비동의/보류와 짧은 근거)를 먼저 표시한다.
  - 호스트 최종 판정의 첫 줄에 **1줄짜리 해결책(구체적 수정방안·조치사항)**을 두괄식으로 명시한다.
  - 이어지는 줄에 채택/기각 이유, 근거, 다음 조치를 기술한다.
- 여기서 줄은 작성자가 명시한 의미 단위다. 한 줄에 여러 장문을 몰아 제한을 우회하지 않는다. 가능한 한 한 문장을 한 줄에 쓰고, 길면 근거를 상세로 옮긴다. 화면 폭에 따른 자동 줄바꿈까지 고정한다고 주장하지 않는다.
- 제목·문제 라벨·본문·답변 라벨·본문·출처 사이에 빈 줄을 둔다. 본문에서 연속된 문장을 각각 줄바꿈해 보여줄 때 `<br>`를 사용한다. Markdown의 단순 개행만으로 렌더링 줄바꿈이 유지된다고 가정하지 않는다.
- 문제와 답변 각각에 `(AI, model, effort)`를 병기한다. 중간에 문제를 제기하는 독립 리뷰어와 상대 검토 답변자는 **'관찰자'**로 기록하며, 최종 판정은 호스트로 구분한다. AI는 실제 발화 주체인 Codex / agy 등으로 적고, model·effort는 확인한 실제 값을 쓴다. subagent·CLI·호스트를 상세 기록에서 구분한다. 모델명은 꾸며내지 않는다.
- 식별자만 적은 `문제 · agy P2-1` 형태는 쓰지 않는다. 심각도 강조가 필요하면 `데이터 손상 위험`처럼 의미로 적고, P1/P2/P3와 내부 finding ID는 상세 추적용으로 둔다.

### 계약과 근거를 읽는 법까지 강요하지 않기

- `D37에 부합`, `[C08]`, `기존 T01로 관리`로 설명을 대신하지 않는다. 해당 원문에서 필요한 조건·규칙·일정의 실제 내용을 가져와 그 자리에서 이해할 수 있게 쓴다.
- 예: “0 × Inf이면 더하는 값이 qNaN이어도 NV를 낸다는 계약입니다.” / “지수 보정값은 −160…160으로 제한합니다.” / “FMA 부호 제어는 opcode 구현 때 반영하기로 한 작업입니다.”
- 링크 텍스트도 `예외 우선순위 규칙`, `지수 보정 범위 계약`, `FMA 부호 제어 구현 일정`처럼 의미로 쓴다. 링크는 정확한 로컬 파일·줄을 가리킨다.
- 사용자가 번호를 몰라도 판정을 이해할 수 있어야 한다. 계약을 인용할 때는 정확한 원문을 쓰고, 번역·풀이이면 그 사실을 구분한다. 긴 계약의 전문과 ID 대응은 상세 영역에 보존한다. 번호를 제거하는 과정에서 계약 조건을 누락하거나 판정을 바꾸지 않는다.

## Codex + agy의 귀속과 판정

- 문제를 제기하는 독립 리뷰어와 상대 검토 과정에서 답변하는 리뷰어는 **'관찰자'**로 기록한다. 최종 판정은 호스트가 내리며 역할을 명확히 구분한다.
- 문제 라벨은 최초 문제를 제기한 관찰자를 가리킨다. 양쪽 관찰자가 같은 원인을 지적했으면 두 작성자를 병기하고 model·effort도 각각 적는다.
- 답변에 상대 검토 관찰자의 동의·비동의·보류와 짧은 근거를 먼저 표시하고, 호스트의 최종 판정과 수정방안(해결책)을 구분한다. 두 발화는 각각 작성자 라벨을 붙이며, 합쳐서 답변 본문 10줄 이내로 유지한다.
- 호스트 답변을 상대 관찰자가 작성한 것처럼 표시하지 않는다. 상호 검토가 없는 과거 보고서의 편집에서는 이를 새로 수행한 것처럼 만들지 않는다.
- Codex only에서는 문제는 Codex 독립 관찰자, 답변은 호스트 Codex의 판정이다. 상세 영역에서 역할·agent ID를 구분하며 agy의 동의를 만들어 넣지 않는다.

아래는 형식 예시이며 모델·effort 값은 실제 실행 값(예: Codex는 config.toml의 gpt-6.1-sol/medium, agy는 gemini-3.8-flash-high/high)으로 채우고, 두괄식 1줄 문제와 1줄 해결책을 첫 줄에 배치한다.

```markdown
## 1. 잘못된 FIFO 깊이 설정에서 응답이 유실될 수 있음

**문제 (관찰자: agy, model: gemini-3.8-flash-high, effort: high)**

응답 FIFO 깊이가 최대 미응답 요청 수보다 작으면 소비자 정지 중 새 응답이 기존 응답을 덮어써 유실될 수 있습니다.<br>
정적 분석 결과이며 현재 기본 파라미터 구성에서는 발생하지 않는 조건부 오류입니다.

**답변 — 상대 검토 (관찰자: Codex, model: gpt-6.1-sol, effort: medium)**

지원 구성의 결함이라는 분류에는 비동의합니다.<br>
설계 계약은 응답 FIFO 깊이가 최대 미응답 수 이상이어야 한다고 명시하므로 정상 지원 범위 밖의 설정입니다.

**답변 — 최종 판정 (호스트 Codex, model: gpt-6.1-sol, effort: medium)**

파라미터 조건 검사(`RSP_DEPTH >= MAX_INFLIGHT`)를 모듈 elaboration 단계에 추가해 잘못된 설정을 시작 시 컴파일 에러로 차단하도록 수정합니다.<br>
P3 방어 제안으로 분류하며 기존 지원 계약 자체의 결함은 아니므로 확정 결함 수에는 포함하지 않습니다.<br>
FIFO 덮어쓰기 방지 assertion을 추가하는 수준에서 정리할 수 있습니다.

출처: [응답 FIFO 깊이 계약](/absolute/project/contracts.md:42)
```

## 기본으로 접는 상세 영역

`<details>`에 `open` 속성을 쓰지 않는다. 렌더러가 HTML 접기를 지원하지 않으면 제목과 구분선이 남도록 쓰고, 접힘을 보장했다고 말하지 않는다. 요약과 상세를 같은 문단에 몰지 않는다.

```markdown
<details>
<summary>상세 근거 — 계약 전문·상호 검토·검증 기록·리뷰 원문</summary>

### 계약 전문과 근거

인용한 계약 원문 전체, 해당 번호와 설명형 파일·줄 링크.

### 독립 리뷰와 상호 검토

각 리뷰어의 독립 결과 원문과 상대 항목별 동의·비동의·보류 및 근거.
호스트의 채택·기각·보류 판정과 이유. 편집 전 원문과 최종 판정을 구분한다.

### 실행 범위와 검증 기록

실행 일시·최초 경로·대상·분류·범위·HEAD/작업 트리 상태, 읽은 핵심 파일의 역할,
명령·결과·미실행 이유, 한계·미결정 사항, 작성자별 AI·model·effort와 agent/conversation ID,
독립 리뷰와 상호 검토의 각각 완료 여부, agy 5분 진행 diff·중단/실패 사유.

</details>
```

완성 후 저장 파일을 다시 읽어 문제·답변 줄 수, 실제 개행, 라벨별 작성자·model·effort, 번호만으로 된 설명의 잔존 여부, 기본 접힘과 상세 근거 보존을 확인한다. 최종 채팅은 보고서 링크와 핵심 결과만 간결하게 전달한다.
