# Cross Review

기능명, 모듈명, 디렉터리 또는 revision/diff를 입력받아 설계 의도와 실제 구현·검증을 대조한다. 기본 응답은 사용자 언어로 작성한다. 리뷰 요청은 대상 소스·사양 수정 권한을 포함하지 않는다. 리뷰 종료 시 최초 실행 디렉터리에 Markdown 보고서를 저장하고, 저장된 본문을 다시 읽어 사용자에게 요약한다.

## 1. 탐색 후 대상 성격 확인 — 본 리뷰 전 필수 단계

먼저 읽기 전용 사전 탐색만 수행한다. 이 단계에서는 결함 판정, 본 리뷰, 테스트 실행, 외부 리뷰어 호출을 시작하지 않는다.

- 디렉터리를 이동하거나 임시 사본을 만들기 전에 현재 작업 디렉터리의 절대 경로를 `invocation_dir`로 기록한다. 최종 보고서는 프로젝트 루트나 리뷰어의 임시 디렉터리가 아닌 이 경로에 저장한다.
- 요청 경로와 실제 프로젝트 루트를 찾고 적용되는 `AGENTS.md`, `README.md`, 문서 인덱스와 빌드 manifest를 읽는다. Git이 있으면 HEAD와 `git status --short`를 확인한다. 기본 대상은 미커밋·미추적 파일을 포함한 현재 작업 트리다. 특정 revision/diff 요청은 그 범위를 따른다.
- `rg --files --hidden`과 `rg -n`으로 기능 별칭, 모듈명, 관련 MD를 찾는다. 대형 vendor/build 트리는 초기 탐색에서 제외하되 **사용자가 직접 지정한 ignored·외부·복사본 경로는 제외하지 않는다**. ignored 경로는 명시적 경로와 `--no-ignore`로 탐색한다. `.git` 내부와 자격 증명은 검색하지 않는다.
- 관련 MD와 직접 연결된 계약·결정·ABI·TODO를 읽고 실제 entry point·핵심 소스·테스트 후보를 선정한다. 긴 문서는 관련 절을 문맥과 함께 읽는다. 읽지 않은 자료를 읽었다고 보고하지 않는다.
- 확장자나 디렉터리 이름만으로 분류하지 않는다. RTL은 합성 가능한 HDL·testbench, Architecture는 구조·계약·설계 결정, Source-Code는 앱·라이브러리·시뮬레이터·펌웨어 등의 실행 코드를 의미한다. 복수 분류가 가능하다. 하드웨어 cycle 모델인 C++는 RTL이 아니라 Source-Code(시뮬레이터)로 분류한다.
- 도구 가용성은 [references/reviewers.md](references/reviewers.md)에 따라 확인한다. 모델 요청은 아직 보내지 않는다. 이미 세션에서 확인한 상태는 불필요하게 반복 조회하지 않는다.

다음 정보를 한 번에 제시하고 사용자에게 **명시적 확인과 리뷰어 선택**을 요청한다.

| 항목 | 제시할 내용 |
|---|---|
| 대상 | 실제 절대 경로, 기능/모듈, revision 또는 작업 트리 |
| 성격 | RTL / Architecture / Source-Code 또는 혼합, 판단 근거, 소프트웨어인 경우 종류·언어 |
| 핵심 자료 | 관련 MD·계약, 중요 구현·테스트 후보와 역할 |
| 범위 | 집중할 경계·관점, 제외 영역, 참조용/구현 대상/스캐폴드 구분 |
| 리뷰어 | Codex only / Codex + agy, 설치·인증 상태 및 미확인 사항 |

대상·분류·범위를 위 표로 먼저 보여준 뒤, **`ask_question` 계열의 선택형 질문 도구**로 확인과 리뷰어 선택을 받는다. 런타임에 실제로 제공되는 `ask_question`, `request_user_input`, `request_user_input_async` 등의 도구를 사용하며, 존재하지 않는 도구를 호출하지 않는다. 선택형 도구가 있으면 일반 채팅으로 모드 이름을 입력하라고 요구하지 않는다.

- 질문: “위 대상·분류·범위로 리뷰를 진행할까요? 리뷰어를 선택해 주세요.”
- 선택지 `Codex only`: “Codex subagent가 독립 리뷰하고, 호스트 Codex가 근거를 확인해 최종 판정합니다.”
- 선택지 `Codex + agy`: “두 리뷰어가 독립 리뷰한 뒤 서로의 지적에 동의·비동의와 근거를 제출합니다. 확인된 범위의 필요한 자료와 리뷰 내용이 agy 서비스에 전달됩니다. 사용량 한도(429) 초과를 방지하기 위해 agy는 Gemini Flash High(`gemini-3.8-flash-high`, effort: `high`)를 강제하며 동시 실행은 최대 3개로 제한됩니다.”
- 선택은 제시한 범위에 대한 확인도 포함한다고 명시하고, 범위 수정은 자유 입력으로 받는다. 수정 요청이면 범위를 갱신하고 다시 확인받는다. 선택지가 미리 선택돼 있어도 실제 제출 전에는 동의가 아니다.
- 선택형 질문 도구가 전혀 없거나 현재 모드에서 사용할 수 없을 때만, 그 제한을 짧게 밝히고 같은 두 선택지를 일반 채팅으로 제시한다.

**확인 전에는 이 단계에서 멈춘다.** 무응답이나 경과 시간을 동의로 간주하지 않는다. 비동기 질문 도구를 사용해도 확인에 의존하는 작업은 진행하지 않는다. 새로 파악한 대상 설명을 사용자가 확인해야 하므로, 최초 리뷰 요청만으로 이 단계를 생략하지 않는다. 리뷰어는 이 스킬을 호출할 때마다 반드시 다시 선택받는다. 같은 세션의 이전 호출에서 받은 선택을 기본값이나 동의로 재사용하지 않는다. 한 호출로 시작한 리뷰의 후속 대화·재개에서는 확인받은 범위와 리뷰어를 유지하되, 대상·분류·외부 전송 범위가 크게 바뀌면 갱신해서 확인한다. 이 대기는 이 스킬의 명시적 사용자 확인 요구 때문이라고 설명한다.

## 2. 확인된 범위의 심층 리뷰

이 절은 다음 절의 독립 리뷰어들이 적용할 검토 기준이다. 호스트는 동일한 자료와 기준을 배포하고 마지막에 근거를 대조한다.

문서의 참조와 실제 호출/데이터 관계를 따라 entry point → 제어·데이터 경로 → 하위 모듈 → 출력·완료·오류 → 테스트·golden·빌드 설정을 추적한다. 핵심 파일마다 역할과 선정 이유를 기록한다. 디렉터리 밖의 생산자·소비자·계약도 범위에 필요한 만큼 확인한다.

프로젝트가 지정한 기준 자료와 우선순위를 따른다. MD에 복사된 코드보다 실제 소스를 확인한다. 기준 도면·생성 MD·결정 기록이 충돌하면 원본과 생성기를 확인하고, 해결되지 않은 충돌은 양쪽 출처를 제시한다. 수정 시간이나 결정 번호 크기만으로 우선순위를 정하지 않는다. 확정 계약, 제안, 가정, TBD, 구현 상태를 구분한다.

분류별로 다음 관점을 적용한다. 모두를 기계적으로 점검하지 말고 대상의 계약과 실패 가능성에 맞춘다.

| 분류 | 주요 검토 관점 |
|---|---|
| RTL | valid/ready, stall payload, credit/FIFO, 동시 push/pop, reset/drain, 순서·tag, mask/tail, 폭·부호, parameter 경계, 합성 가능한 구조 |
| Architecture | 명령·데이터·완료 흐름, 인터페이스와 소유권, 전제와 trade-off, 처리량·latency·면적 주장의 조건, 구현 가능성·통합 경계 |
| Source-Code | 실제 빌드·등록 경로, API/ABI, 객체·buffer 수명과 소유권, 상태 전이, 오류·완료 exactly-once, 동시성·이벤트 재예약, 경계·오버플로, 테스트 독립성 |
| 시뮬레이터·펌웨어 | functional/cycle 경로 구분, timed access와 retry 부작용, persistent progress, descriptor 매핑, command dependency, DMA/SPM hazard, callback 계약 |
| 수치 경로 | rounding, NaN/Inf/signed zero/subnormal, 예외 플래그, overflow/underflow, 지원 입력 범위, 허용 오차와 golden의 독립성 |

단위 테스트 shell과 golden이 대체하는 미구현 영역을 식별한다. 과거 APPROVED/PASS나 생성물끼리의 일치를 현재 정확성·통합 성공의 근거로 대체하지 않는다. 처리량에서는 내부 II와 실제 공급률·메모리 병목을, 합성에서는 조합 지연과 시스템 성능을 구분한다.

의심점은 반대 근거와 호출자·소비자까지 확인한다. 검증 스크립트의 부작용과 도구 가용성을 읽은 후 문제를 판정할 최소 테스트를 실행한다. 임시 경로나 기존 ignored build를 사용하고 추적 파일을 바꾸지 않는다. 실행하지 못한 검증과 이유를 기록한다. 패키지 설치, 벡터 재생성, 서버 변경, 설계 수정은 리뷰만을 위해 자동 수행하지 않는다.

## 3. 독립 리뷰 → 상호 검토 → 최종 판정

[references/reviewers.md](references/reviewers.md)에 따라 확인된 모드를 실행한다. 호스트 Codex는 요청·자료 배포·진행 관리·최종 판정을 맡고, Codex subagent는 독립 리뷰를 맡는다. 이 스킬의 리뷰 작업에는 해당 subagent 위임이 포함된다. 사용자 선택 없이 agy로 자료를 전송하지 않는다.

1. **독립 리뷰**: 같은 범위·기준 snapshot·계약·원시 자료를 Codex subagent와 (선택한 경우) agy에 제공한다. 서로의 findings나 호스트의 의심·원하는 결론은 제공하지 않는다. agy는 429 사용량 한도 소진을 방지하기 위해 **Gemini Flash High(`gemini-3.8-flash-high`, effort: `high`)를 강제**하며, 시스템 전체에서 **동시 실행되는 agy 프로세스는 최대 3개**로 제한한다. agy 내부 서브에이전트 또한 무단 과다 생성을 금지하고 최대 3개 이내로 제한하거나 단일 직접 검토를 지시한다. 가능한 경우 병렬로 수행하되 동시 실행 한도를 준수한다.
2. **상호 검토 — Codex + agy 필수**: 두 독립 결과를 확정·보존한 뒤, Codex subagent에 agy 원문을, agy에 Codex subagent 원문을 전달한다. 각자 상대의 지적 **하나마다 동의 / 비동의 / 판단 보류, 근거, 필요한 최소 검증**을 제출한다. 부분 동의면 동의하는 조건과 반대하는 부분을 구분한다. findings가 없는 경우에도 상대의 검토 범위·검증 한계를 확인한다. 상대의 상호 검토 답변은 양쪽 제출 전에는 공유하지 않는다.
3. **호스트 Codex 최종 판정**: 양쪽 독립 리뷰와 양방향 상호 검토를 모두 받은 뒤 소스·계약·재현 결과에 대조한다. 중복 원인을 합치고, 동의 횟수 대신 근거로 채택·기각·보류를 결정한다. 미해결 충돌은 양쪽 근거와 최소 후속 실험을 남긴다.

Codex only는 Codex subagent의 독립 리뷰 → 호스트 Codex의 근거 확인·최종 판정으로 끝낸다. agy 호출이나 가상의 상호 검토를 추가하지 않는다. Codex subagent를 사용할 수 없으면 그 제한을 알리고, 별도 read-only Codex CLI를 독립 리뷰어로 사용할 수 있는지 확인한다. 둘 다 불가능하면 호스트 단독 수행임을 명시하며 독립 리뷰 완료로 표현하지 않는다.

agy는 실행 시 `--model gemini-3.8-flash-high --effort high`를 필수 지정하고, 시스템 내 실행 중인 agy 프로세스가 3개 이상이면 기존 프로세스가 종료될 때까지 대기(큐잉)한 후 순차 실행한다. 독립 리뷰와 상호 검토 각 실행 모두 비동기로 관리하고 5분 전의 진행 스냅샷과 비교한다. 실질적인 진행 diff가 있으면 계속 기다린다. 자세한 상태·정체·재개 처리는 위 reference를 따른다. 독립 리뷰 또는 상호 검토의 한쪽이 실패하면 확보한 결과와 빠진 단계를 부분 보고서에 남긴다. **Codex + agy에서 양방향 상호 검토가 끝나지 않으면 교차 리뷰 완료로 표현하지 않는다.**

## 4. 요점 중심 보고서

작성 전에 [references/report-format.md](references/report-format.md)를 읽고 따른다.

- 결론·영향·다음 조치를 먼저 제시한다. 문제 하나는 최대 3줄, 답변 하나는 최대 10줄로 작성하고, 문장별 줄바꿈과 문제·답변 사이 빈 줄을 유지한다.
- 문제·답변 각각에 실제 작성자의 **`(AI, model, effort)`**를 병기한다. 예: `문제 (agy, model: gemini-3.8-flash-high, effort: high)` / `답변 (Codex, model: gpt-6.1-sol, effort: medium)`. Codex는 `~/.codex/config.toml`에서 확인한 model·effort를 쓰고, agy는 요청 인자(`--model gemini-3.8-flash-high --effort high`) 및 실행 메타데이터를 기록하며, 확인할 수 없을 때만 `미기록`으로 표시한다. 추측하거나 현재 호스트 설정을 과거 리뷰에 붙이지 않는다.
- `문제 · agy P2-1` 같은 내부 식별자로 독자를 읽게 하지 않는다. 제목은 발생 조건·영향을 바로 알 수 있는 말로 쓴다. 계약·결정·TODO도 `D37`, `C08` 같은 번호 대신 **실제 문구와 뜻**을 본문에 가져온다. 긴 원문 전체와 실행 기록은 기본으로 접힌 `<details>`에 보존한다.
- 확정 문제를 심각도 순으로 먼저 제시한다. 심각도는 데이터 손상·교착·핵심 계약 위반(P1), 조건부 오류·유의미한 검증 누락(P2), 영향이 작은 명확한 불일치(P3)로 판단하되, 번호 매핑은 상세 근거에 둔다. P0는 긴급하고 광범위한 영향의 근거가 있을 때만 쓴다.
- 문제에는 조건과 영향, 답변에는 최종 판정·이유·다음 조치를 담는다. 관련 파일·정확한 줄로 가는 설명형 링크를 제공한다. 재현과 정적 분석을 구분하고 미확정 설계를 대신 결정하지 않는다.
- 근거 부족한 의심은 `확인 필요`로 분리한다. 미구현 자체, 취향, 합의된 trade-off, 지원 범위 밖 입력을 버그로 부풀리지 않는다. 단, 현재 동작이나 정확성 주장·통합 계약에 구체적인 영향을 주면 지적한다. finding 개수를 채우지 않는다. 문제가 없으면 확인 범위에서 확정적인 문제를 찾지 못했다고 밝힌다.

### 보고서 저장과 사용자 요약 — 종료 시 필수

- Codex only와 Codex + agy 모두 `invocation_dir/cross-review-report-YYYYMMDD-HHMMSS.md`에 위 결과의 전체 본문을 저장한다. 같은 이름이 있으면 suffix를 붙여 기존 보고서를 덮어쓰지 않는다. 기존 보고서의 편집·재구성 요청이면 원본을 보존하고 `_r2.md`, `_r3.md`로 저장하되 사용자가 지정한 파일명·수정 대상이 있으면 따른다. 소스·사양 수정 금지와 별개로 이 보고서 저장은 기본 산출물이다. 보고서를 자동 commit하지 않는다.
- 보고서에는 실행 일시·최초 실행 경로, 확인된 대상·분류·범위·HEAD/작업 트리 상태, findings와 근거·파일/줄, 확인 필요 사항, 읽은 핵심 자료, 검증 명령·결과·미실행 이유, 선택한 리뷰어, 각 작성자의 AI·model·effort, 독립 리뷰와 양방향 상호 검토의 원문·항목별 동의/비동의/보류 근거, 호스트 최종 판정 및 단계별 완료 여부를 포함한다. 장문은 기본으로 접힌 상세 영역에 둔다. agy를 사용했다면 conversation ID, 5분 diff 관찰 시각과 변화 요약, timeout·정체·실패·중단 이유도 기록한다. 비밀이나 관련 없는 로그는 복사하지 않는다.
- 리뷰를 시작한 뒤 실패·정체·사용자 중단 등으로 끝나도 확보한 결과와 미완료 범위를 부분 보고서로 남긴다. agy 결과가 없으면 `Codex 검토 완료 / agy 미완료`처럼 상태를 명시하며 완료된 교차 리뷰로 표현하지 않는다. 본 리뷰 전 대상 확인 대기는 종료로 취급하지 않는다.
- **저장 후 파일을 실제로 다시 읽는다.** 내용과 저장 경로를 확인하고, 그 본문을 근거로 핵심 findings·영향·다음 조치와 검증 결과·한계·교차 리뷰 완료 여부를 사용자에게 간결하게 정리한다. 최종 응답에 보고서의 클릭 가능한 절대 경로 링크를 포함한다. 저장 실패 시 성공했다고 말하지 말고 실패 경로·이유를 알리고 본문을 응답으로 제공한다.

## 예시

- `$cross-review sfvu의 n-lane(nlane) architecture/rtl을 리뷰해줘.`
- `$cross-review sw/abs3vp_local/extend/abs3mxacc 모듈을 리뷰해줘.`
- `$cross-review sw/abs3vp_local/extend/abs3vcacc의 command 완료와 retry를 리뷰해줘.`
- `$cross-review src/payment의 상태 전이와 테스트를 리뷰해줘.`

SFVU에서 실행할 때만 해당 저장소의 규칙을 적용한다. 예를 들어 ABS3 로컬 복사본은 수정 금지지만 직접 리뷰할 수 있다. VCACC가 스캐폴드라면 현재 코드의 결함을 검토할 수 있으나 그 안의 수치·latency·op 목록을 확정 SFVU 사양으로 해석하지 않는다. 이 특수 규칙을 다른 프로젝트에 강제하지 않는다.
